# Stage 1 실사용 기기 정비 작업지시서

대상 기기의 모든 Codex 데몬과 앱 서버를 정비 창에서 종료한 뒤, `default`, `janmori101`, `szob`의 데몬이 하나의 설치된 실행 파일을 사용하도록 전환한다. 같은 정비 창에서 공유 세션 DB와 롤아웃 경로를 대조하고, 복구가 입증된 항목만 반영한다.

## 기준 상태와 작업 범위

- 공개 `wrapper` 프리릴리스 `addffcba`의 바이너리가 `$PREFIX/bin/codex`에 적용돼 있다. 마지막 확인에서 공용 `$HOME/.codex/packages/standalone/current`는 `0.170.0-3f7e1a`를, 롤백 포인터는 `0.169.1-3de502`를 선택했다. 작업 시작 때 상태와 바이너리 해시를 다시 기록한다.
- 세 홈은 아직 각각 전용 `packages/app-server-daemon/current`를 갖고 있다. 통일 대상은 이 세 링크의 **실행 파일 선택**이다. 각 홈의 데몬 프로세스, 제어 소켓, 설정과 인증은 각 홈 소유로 유지한다. `167.2`는 바이너리 통일 대상에서 제외한다. 정비 창 시작 시에는 `167.2`를 포함한 모든 Codex 데몬과 앱 서버를 종료 대상으로 확인한다. [Stage 1 패키지 계약](../../SPEC.md)
- 공유 세션 저장소는 `$HOME/.codex` 아래의 `sessions/`, `archived_sessions/`, `thread-writer-locks/`, `session_index.jsonl` 및 `state_5.sqlite`다. 실제 경로와 장치 번호·inode를 홈별로 다시 대조한다. 이전 조사에서는 DB 파일을 연 프로세스가 4개 확인됐다. 여기에 없는 writer도 정비 창에서 재검색한다.
- 현재 작업 세션도 앱 서버 종료의 영향을 받을 수 있다. 정비는 종료 대상에서 독립된 Termux 셸이나 운영 콘솔에서 수행하고, 작업지시서·백업 위치·진행 기록을 그쪽에서 열 수 있게 준비한다.

## 1. 정비 창 준비 및 전체 데몬·앱 서버 종료

1. 전환 대상, 정비 시작·종료 시간, 강제 종료 범위, 복구 담당자를 기록한다. 종료 직전까지 신규 제출을 막고, 진행 중인 턴과 큐의 상태를 확인한다. 완료 여부가 불확실한 제출 ID는 기록해 재기동 뒤 결과와 대조한다.
2. `/proc`와 홈별 데몬 상태로 기본 홈·프로필·별도 `CODEX_HOME`·`167.2`·서비스 감독 하의 데몬 및 포그라운드 앱 서버를 식별한다. PID, 시작 시각, 실제 실행 파일, 실행 홈, 서비스 소유자, DB/WAL 열린 FD를 기록한다. 공유 저장소를 사용하는 `codex exec` 등 별도 writer와 이들의 재기동 경로도 목록에 포함한다. 환경과 인수에는 진단에 필요한 항목만 남긴다.
3. 자동 재기동이나 자동 시작 경로를 정비 창 동안 중지한다. S27 등 감독 서비스가 종료 대상 앱 서버를 다시 띄우면 그 서비스의 문서화된 관리 경로로 재기동을 억제하고 복구 방법을 기록한다. 각 관리 데몬은 그 홈과 기존 런타임에 맞는 정상 종료 명령으로 정지한다. 포그라운드 앱 서버는 실행 주체를 통해 정상 종료한다.
4. 유예 시간 후 남은 데몬·앱 서버 및 공유 DB writer에는 **강제 종료를 적용한다**. 신호 직전에 PID와 시작 시각, 실제 실행 파일, 종료 범위를 다시 대조한다. `SIGTERM` 후에도 남은 식별된 대상은 `SIGKILL`로 종료하고 재검색한다. 포괄적 `pkill codex`로 프로세스 이름만 매칭하는 방식은 피한다.
5. 모든 대상 데몬과 앱 서버가 종료됐고, 공유 DB/WAL의 열린 FD와 스레드 writer 잠금이 사라졌으며, 자동 재기동이 중지됐음을 확인한다. 잔존 프로세스나 소유권이 불확실하면 링크와 DB 변경을 보류한다. 잠금 파일은 사라졌는지 여부와 실제 커널 잠금 상태를 구분해 확인한다.

## 2. 백업과 복구 시험

1. 소유자 전용 정비 디렉터리에 원래 `current` 링크 값, 패키지 선택 기록, 데몬 설정, 재기동 경로, Wrapper 활성·롤백 포인터, 이전 바이너리 백업 위치를 기록한다. 각 전용 릴리스와 공용 세대의 실행 파일 해시 및 inode를 남긴다. 계정 인증 파일은 해당 홈에 둔다.
2. SQLite 백업 API로 `state_5.sqlite`의 일관된 사본을 만든다. 같은 시점의 롤아웃 트리, 인덱스와 관련 상태를 보존하고 해시와 파일 수를 기록한다. WAL 모드의 원본 DB 파일만 복사해 복구본으로 삼는 방식은 피한다.
3. 복구본의 `PRAGMA quick_check`와 대표 UUID 조회를 확인한다. 별도 HOME·CODEX_HOME에서 링크 전환, DB 수정 후보, 재기동과 원복을 먼저 검증한다. DB를 여는 `167.2` 또는 다른 런타임이 있다면 확인한 실행 버전 조합으로 스키마·마이그레이션 호환성을 복제본에서 검증한다.

## 3. 공유 세션 DB와 인덱스 정리

아래 수치는 기기 점검 기록 `$HOME/.local/state/codex-wrapper-cutover.6m1uUR/inventory-summary.txt`에서 가져왔다. 수정 대상은 정비 창에서 다시 읽은 상태로 결정한다. DB 행은 UUID와 현재 경로, 롤아웃은 파일 헤더의 UUID와 활성·보관 위치, 인덱스는 조회 경로별 실제 소비 결과를 기준으로 대조한다.

| 이전 관측 | 정리 작업 |
| --- | --- |
| 끊어진 경로에 같은 UUID 파일이 한 개씩 있는 72건(활성 69건, 보관 3건) | 파일 헤더, 보관 상태, 경로 충돌과 대표 기록을 검증한다. UUID별 이전·새 경로 목록을 작성하고 복제본에서 조회와 재개를 확인한다. |
| 현재 롤아웃 목록에 대응 파일이 없는 활성 DB 행 3건 | 기존 저장 위치와 백업에서 UUID를 찾는다. 복구 근거가 있는 항목만 복원 계획에 넣고, 미해결 행은 목록에 남긴다. |
| 같은 UUID를 가진 롤아웃 파일 1쌍 | 두 파일을 보존한 상태에서 내용, 이력 차이, 참조 경로를 비교한다. 근거가 충분할 때만 대표 파일을 선정하고 나머지는 별도 보존한다. |
| `session_index.jsonl` 반복 ID 17개, DB와 롤아웃 목록에서 확인되지 않은 ID 1개 | 반복 행의 쓰기·조회 의미와 마지막 이름 갱신을 확인한다. 처리 방침이 확정된 항목만 정리하고, 조회 경로를 재검증한다. |

1. 업스트림에서 지원하는 복구 경로가 있는지 먼저 확인한다. 직접 DB 경로 교정이 필요한 경우에는 정비 창과 백업을 확인한 뒤 승인된 UUID·기존 경로 조건을 사용해 단일 트랜잭션으로 반영한다. 예상 행 수가 달라지거나 다른 필드가 변경되면 롤백한다. 전체 DB 재생성, 일괄 삭제, 이름의 임의 재생성은 별도 근거와 계획이 필요하다.
2. 재기동 전에 `quick_check`, 수정 대상과 비대상 행, UUID·경로·보관 정합성, 인덱스 전후 차이를 다시 대조한다. 복구하지 못한 항목은 보류 사유와 증거 위치를 남긴다. 이후 세 홈의 목록·읽기·재개에서 대표 UUID를 확인한다. 이름과 UUID 조회는 앱 서버, TUI, `codex exec resume` 경로별로 확인한다. [세션 인덱스 검증 계획](SHARED_DAEMON_PACKAGES_PLAN.md#42-session_indexjsonl-권위-원천-및-삭제이름변경-검증안)

## 4. 데몬 바이너리 전환과 정상 재기동

1. 공용 `$HOME/.codex/packages/standalone/current/bin/codex`의 실경로, 버전과 해시를 확인한다. 각 대상 홈에서 전용 선택과 백업이 일치할 때만 `$CODEX_HOME/packages/app-server-daemon/current`를 같은 디렉터리의 임시 링크에서 원자적으로 교체한다. 새 링크는 특정 릴리스 디렉터리 대신 공용 `$HOME/.codex/packages/standalone/current`를 가리킨다. 일반 파일·디렉터리 또는 준비 중 바뀐 링크를 발견하면 그 홈의 전환을 중지한다.
2. 세 홈을 명시적으로 선택해 갱신된 래퍼로 순차 기동한다. 각 홈에서 `daemon version`, 제어 소켓의 응답, `/proc/<pid>/exe`의 실제 장치 번호·inode를 기록한다. 합격 조건은 **세 데몬이 공용 실행 파일과 같은 inode를 사용**하고, **홈별 PID와 소켓은 서로 분리**되는 것이다. 기존 전용 선택을 다시 만드는 `daemon update --from-cli`는 이 절차에 포함하지 않는다.
3. 각 홈이 의도한 공유 DB를 열고 인증 경계를 유지하는지 확인한다. 대표 활성·보관 UUID 읽기, `doctor --json`의 앱 서버와 롤아웃 정합성, 새 데몬의 FD 34 파일을 확인한다. 기존 세션 밖에서 연 새 Termux 셸은 `command -v codex`가 `$PREFIX/bin/codex`를 선택하는지 확인한다. 테스트 턴은 별도 테스트 UUID에 한정하고 접수와 완료를 각각 검증한다.
4. 관리 경로를 복원해 정비 전에 실행 중이었던 `167.2`와 그 밖의 서비스를 원래 세대와 원래 홈에서 기동한다. 기존 서비스의 새 PID와 실제 실행 파일, 공유 저장소 호환성 및 중복 데몬 여부를 확인한다. DB를 건드리는 구형 런타임의 재기동은 복제본 호환성 검증 결과에 따른다.

## 5. 원복과 후속 정리

- 링크 전환에 실패하면 해당 홈의 신규 데몬을 종료하고 전용 `current`를 백업 값으로 원자 복원한다. 기동 후 예전 실행 파일·홈·소켓이 실제로 복구됐는지 확인한다. DB도 바뀌었다면 복구 범위를 먼저 판정한다.
- DB 정리를 원복할 때는 모든 공유 writer를 다시 종료한다. 백업 이후의 세션 및 DB 변경을 대조해 보존할 신규 작업을 확인하고, DB와 인덱스·롤아웃을 동일 시점으로 복원할 수 있을 때만 원복한다. 재기동 결과가 불확실하면 백업과 실패 시점 사본을 모두 보존한다.
- 전용 릴리스 디스크 정리는 전환 검증과 원복 보존 기간 이후에 진행한다. 세 홈과 별도 홈의 링크, 실행 파일과 열린 FD, 선택 기록 및 원복 의존성을 다시 스캔해 참조가 사라진 사본만 대상으로 삼는다. `167.2` 및 복구 백업은 이 삭제 대상에서 제외한다.
- 작업 기록에는 종료·강제 종료 대상, 새·이전 PID와 실행 파일 inode, 전후 불일치 건수, 보류 항목, 백업 및 원복 결과를 남긴다. 실계정 추론과 외부 Remote Control 페어링은 별도 테스트 스레드와 클라이언트에서 확인한다. 물리 Command Center의 `/switch` 인계와 실계정 간 동일 UUID 재개는 실제 writer 해제와 업스트림 재개 판정까지 관측한 범위대로 기록한다.
